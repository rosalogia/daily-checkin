* Overview

A Discord bot designed to facilitate daily progress tracking and accountability. The bot posts daily messages pinging registered users to share their progress toward personal goals, maintains streak tracking, and provides administrative controls for server management.

* Core Features

** Daily Check-in System
- Posts automated daily messages in configured channels at configured times
- Pings all registered users to request progress updates
- Creates threads under daily posts for user responses (with date in thread name)
- Displays current streak counts for each user in the daily post
- 24-hour response window from daily post creation

** User Registration & Goal Management
- Users register via slash commands with personal goals
- Goal editing and deregistration capabilities
- No content validation on responses - any reply counts toward streak

** Streak Tracking
- Tracks consecutive days of user participation
- Immediate streak reset for missed days
- Grace period: 2 days for streaks over 30 days
- Individual streak display in daily posts (e.g., "John (Day 5), Sarah (Day 12)")

** Administrative Controls
- Server admins can configure the daily check-in channel
- Per-server timezone configuration for daily posts
- Channel-specific bot permissions

* User Experience Flow

** Registration
1. User runs ~/register-goal~ slash command
2. Provides their personal goal/objective
3. Bot confirms registration and explains daily check-in process

** Daily Interaction
1. Bot posts daily message at configured time
2. Message pings all registered users with their current streaks
3. Users press the 🔥 *Check in* button or reply in the created thread
4. Button check-ins count immediately; thread replies are counted when the next daily post goes out

** Goal Management
- ~/edit-goal~: Modify existing goal text
- ~/deregister~: Remove from daily check-ins

** Administrative Setup
- ~/set-checkin-channel~: Configure where daily posts appear
- Timezone configuration per server

* Deployment

** Architecture
The bot runs serverless on AWS and is deployed with SAM (=template.yaml=):

- *Interactions function* (Lambda + Function URL): Discord's Interactions Endpoint. Handles slash commands and button clicks over HTTP; no gateway connection.
- *Daily function* (Lambda): run every minute by EventBridge Scheduler. When a server's configured time arrives it credits thread replies to the previous post, resets missed streaks, archives the old post, and posts the new one. =/trigger-checkin= invokes it directly.
- *DynamoDB tables*: on-demand. =guilds= (key =guild_id=) holds each server's config and current daily post; =users= (key =guild_id=, =user_id=) holds goals and streaks. See =src/store.rs=.
- *SSM Parameter Store*: holds the bot token as a SecureString.

Expected cost is about $0/month within AWS's always-free limits.

** First-time Setup
All tools come from the dev shell (=nix develop=, or =direnv allow=).

1. Store the bot token in SSM:
   #+BEGIN_SRC sh
   aws ssm put-parameter --name /daily-checkin/discord-token --type SecureString --value "$DISCORD_TOKEN"
   #+END_SRC
2. Set =DiscordPublicKey= in =samconfig.toml= to the Discord application's public key (General Information page), then build and deploy:
   #+BEGIN_SRC sh
   sam build && sam deploy
   #+END_SRC
3. Copy the =InteractionsEndpointUrl= stack output into the Discord application's *Interactions Endpoint URL* and save. Discord sends a signed ping to verify it.
4. Register slash commands (reads =DISCORD_TOKEN= from =.env=; see =.env.example=):
   #+BEGIN_SRC sh
   cargo run --bin register-commands
   #+END_SRC

** Updating
Pushing to =main= deploys automatically (see below). To deploy by hand:
#+BEGIN_SRC sh
sam build && sam deploy
#+END_SRC
Re-run =register-commands= if commands were added or changed.

** CI/CD
GitHub Actions (=.github/workflows/ci.yml=) tests, lints the template, and builds the Lambda binaries on every pull request and push. On pushes to =main=, once that passes, it deploys the stack and re-registers slash commands. Deploys never run concurrently.

The workflow authenticates to AWS with GitHub's OIDC tokens, so no AWS keys are stored in GitHub. =ci/github-deploy.yaml= sets this up and was deployed once by hand:
#+BEGIN_SRC sh
aws cloudformation deploy --stack-name daily-checkin-github-deploy \
  --template-file ci/github-deploy.yaml --capabilities CAPABILITY_NAMED_IAM
#+END_SRC
It creates:
- the GitHub OIDC identity provider
- =daily-checkin-github-deploy=: assumable only by workflows on =main= of this repo; can only run CloudFormation on this stack, upload build artifacts, and read the bot token
- =daily-checkin-cfn-execution=: used by CloudFormation to manage the stack's resources, limited to =daily-checkin-*= resources

Its two role ARNs are stored as the repository variables =AWS_DEPLOY_ROLE_ARN= and =CFN_EXECUTION_ROLE_ARN=.

The Rust version is pinned in =rust-toolchain.toml=, which both the Nix dev shell and CI use, and =Cargo.lock= is committed so CI builds the same dependency versions as local builds.

** Migrating from the VPS
1. Stop the VPS bot, so it and the Lambda don't both post. Avoid migrating in the 15 minutes after a server's post time: imported servers haven't recorded today's cycle, so the Lambda would post again.
2. Deploy as above, but don't set the Interactions Endpoint URL yet.
3. Import the old data file (=GUILDS_TABLE= and =USERS_TABLE= are the =GuildsTableName= and =UsersTableName= stack outputs). =--resume-on= is the local date of the first post the Lambda will make; active streaks are carried across the gap so the downtime doesn't reset them. Check the output with =--dry-run= first:
   #+BEGIN_SRC sh
   cargo run --bin import-data -- bot_data.json --resume-on 2026-10-07 --dry-run
   GUILDS_TABLE=... USERS_TABLE=... cargo run --bin import-data -- bot_data.json --resume-on 2026-10-07
   #+END_SRC
   The import must finish before that first post. If go-live slips past it, re-run the import with the new date.
4. Set the Interactions Endpoint URL and register commands.

* Technical Requirements

** Data Storage
- Two DynamoDB tables with on-demand billing and numeric Discord IDs as keys (see =src/store.rs=)
- Items are serialized with =serde_dynamo= from the structs in =src/data.rs=, one struct per table
- Config commands, cycle claims, and daily posts each update only their own attributes of a guild item, so they can't overwrite each other
- Check-ins and streak resets use optimistic locking so concurrent updates can't double-count
- Each daily cycle is claimed with a conditional write so it runs once even if the scheduler fires twice

** Bot Permissions
- Send Messages
- Create Public Threads
- Mention Everyone (for daily pings)
- Use Slash Commands
- Read Message History (thread replies are read in a batch at each daily post)

** Streak Logic
- Count consecutive days with a button press or thread response within 24-hour window
- The button always counts; thread responses count unless the user turned them off with ~/thread-checkins~
- Reset to 0 for missed days (unless 30+ day grace period applies)
- Grace period: Allow up to 2 missed days for streaks ≥30 days
- Automatic streak maintenance when daily posts are created
- Track last response date to calculate streaks accurately

* Commands

| Command                | Description                                      | Permissions |
|------------------------+--------------------------------------------------+-------------|
| ~/register-goal~       | Register with a personal goal                    | All users   |
| ~/edit-goal~           | Modify existing goal                             | All users   |
| ~/deregister~          | Remove from daily check-ins                      | All users   |
| ~/stats~               | View goal, streaks, and status (self or others)  | All users   |
| ~/thread-checkins~     | Choose whether your thread replies count         | All users   |
| ~/set-checkin-channel~ | Configure daily post channel                     | Admin only  |
| ~/set-checkin-time~    | Configure daily post time & timezone             | Admin only  |
| ~/trigger-checkin~     | Post the daily check-in immediately              | Bot owner   |

* Project Structure

** Overview
The bot is organized into a modular structure for maintainability and scalability:

#+BEGIN_SRC
template.yaml            # SAM template: functions, table, schedule
Makefile                 # Lambda build targets used by `sam build`
src/
├── lib.rs               # Library root and bot token loading
├── data.rs              # Data structures
├── store.rs             # DynamoDB persistence
├── daily.rs             # Daily posting cycle and scheduling
├── streaks.rs           # Check-in recording and streak logic
├── bin/
│   ├── interactions.rs  # Lambda: Discord Interactions Endpoint
│   ├── daily.rs         # Lambda: scheduled and manual daily posts
│   ├── register_commands.rs # CLI: register slash commands
│   └── import_data.rs   # CLI: import a bot_data.json into DynamoDB
├── commands/
│   ├── mod.rs           # Command registration and interaction routing
│   ├── ping.rs          # Basic ping command
│   ├── user.rs          # User commands (register/edit/deregister goals, stats)
│   └── admin.rs         # Admin commands (set-checkin-channel/time, trigger-checkin)
└── utils/
    ├── mod.rs           # Utility module exports
    ├── responses.rs     # Common response builders
    └── command_helpers.rs # Command argument extraction utilities
#+END_SRC

** Key Design Principles
- *Separation of concerns*: Each module has a single responsibility
- *Modular commands*: Easy to add new commands without modifying existing code
- *Centralized routing*: All command dispatch handled in =commands/mod.rs=
- *Shared utilities*: Consistent response formatting and reusable helpers
- *Thin entry points*: the Lambda binaries only parse events and wire up dependencies

** Adding New Commands
1. Create command functions in appropriate module (=user.rs=, =admin.rs=, or new module)
2. Register command in =commands/mod.rs= (=all_commands= and =handle_interaction=)
3. Return a response built with =utils/responses.rs= (handlers return the response instead of sending it)
4. Deploy, then re-run =register-commands=
